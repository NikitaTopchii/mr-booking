## Phase 2C authentication release evidence

- `yarn install --immutable` completed using Yarn 4.17.1.
- Clean file-backed auth migrations applied twice and deterministic seeds ran
  twice; `yarn test:integration` passed.
- Focused domain, handler, persistence, API, browser-client, component,
  routing, boundary, lint, and typecheck checks passed.
- `yarn test:e2e` passed all nine Chromium authentication journeys.
- `docker compose config --quiet` passed; production API and web images built,
  including native Argon2id and `better-sqlite3`.
- The public gateway passed Ukrainian/English page loads, registration,
  production cookie checks, current-user lookup, protected rendering, reload,
  logout, post-logout rejection, localized protected redirect, Alice/Bob
  login, and session persistence across `docker compose restart`.
- A Playwright CLI browser pass confirmed the production cookie is accepted on
  localhost, survives a real reload, and is cleared by logout.

Docker remains a bonus delivery category in this matrix until the complete
mandatory product scope is delivered; the Phase 2C evidence records only the
authentication release gate and does not claim booking or calendar delivery.

## Phase 2D application-shell evidence

- The protected Server Component layout resolves the safe current user once
  and composes the localized shell for Schedule and My bookings.
- Desktop navigation and the mobile two-destination bottom navigation expose
  the current route with visible state and `aria-current="page"`.
- The Radix user menu shows read-only name/email identity, preserves the
  current route when changing locale, and reuses the existing logout feature.
- `/uk/my-bookings` and `/en/my-bookings` render upcoming and past UI
  foundations with deliberate localized empty states and a localized Schedule
  action.
- No booking query, booking DTO, fake record, cancellation action, pagination,
  timezone formatter, booking table, or client-side booking store exists yet.

`MY-BOOKINGS-001` through `MY-BOOKINGS-006` remain planned until the
authoritative booking domain and API provide real ordered, paginated,
timezone-aware rows and navigation context.

## Phase 3A booking-core evidence

- `booking-domain` owns title normalization, Europe/Kyiv interval validation,
  strict future checks, half-open overlap semantics, and deterministic slot
  generation without framework or persistence imports.
- `0002_booking_foundation.sql` adds UTC-millisecond `bookings` and
  `booking_slots` tables, duration/title checks, real foreign keys, partial
  active indexes, and unique `(room_id, slot_starts_at_utc)` ownership.
- `CreateBookingHandler` and `CancelBookingHandler` use the server clock,
  trusted author identity, explicit application transaction boundaries, typed
  stable errors, ownership checks, future-only new cancellation, and
  idempotent repeat owner cancellation.
- The file-backed booking integration suite covers migration repeatability,
  FK/CHECK constraints, rollback/no-orphan behavior, different-room and
  adjacent success, cancellation release/preservation, reopen persistence, and
  a real two-worker independent-connection race with one winner.
- Booking forms, weekly schedule UI, and My bookings data remain deferred.

## Phase 3B booking-API evidence

- `GET /api/rooms`, `GET /api/rooms/:roomId/bookings`,
  `POST /api/bookings`, and `DELETE /api/bookings/:bookingId` all use the
  opaque-session guard and server-derived identity.
- Zod transport schemas reject malformed ranges, bodies, IDs, extra author
  fields, ownership flags, numeric timestamps, and datetimes without a
  timezone before CQRS dispatch. Valid `Z` or explicit-offset values normalize
  immediately to internal UTC milliseconds.
- `GetRoomScheduleQuery` validates the independent absolute range, checks the
  room, loads one safe joined read model, computes `isMine`, excludes
  cancellations, and uses half-open overlap with stable ordering.
- `booking.controller.spec.ts` exercises the real NestJS HTTP layer and a
  temporary file-backed SQLite database for authentication, safe DTOs,
  boundary-crossing schedules, validation codes, conflict mapping,
  authorization, idempotent cancellation, slot release, and schedule removal.
- `booking-api.spec.ts` smoke-tests login, booking creation, canonical UTC
  responses, and ISO 8601 schedule queries through the application gateway.
- No calendar, booking dialog/form, SWR client, or My bookings integration is
  included in Phase 3B.

## Phase 3C interactive-schedule evidence

- The localized Server Component schedule route passes only its dictionary
  slice to `booking-feature-web`; SWR owns room and schedule server state.
- `booking-ui` generates 30-minute `Europe/Kyiv` office slots as absolute
  instants, including DST tests, while URL weeks and labels use the browser
  timezone.
- The repository-owned seven-day CSS grid provides room and week URL state,
  loading/empty/error/revalidation states, current day/time, ownership cues,
  keyboard-focusable availability, and contained mobile scrolling.
- Runtime-validated browser transport sends ISO 8601 range and mutation
  timestamps and normalizes network, malformed response, and stable API
  errors.
- Component and browser journeys cover URL normalization, creation, details,
  owner cancellation, locale preservation, responsive viewports, and a second
  browser timezone. My bookings integration remains deferred.

## Status and evidence rules

- Change `Planned` only when the requirement has implementation and tests.
- Evidence MUST link to concrete tests, code paths, screenshots, or commands.
- A bonus MUST NOT substitute for an incomplete mandatory row.
- Architecture preparation alone is not implementation evidence.
